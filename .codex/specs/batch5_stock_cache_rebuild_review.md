# CM-20260924-23 普通库存缓存重建性能评审规格

## 1. 评审范围与结论

本规格冻结普通库存 `StockCacheReconciler` 的启动校准和持久化投影恢复边界。目标是消除暖启动时对全量 `stock_cache_repair` 记录和 Redis 投影的无条件重写，同时保留 Redis 冷启动、局部 Key 丢失、进程中断和多实例竞争下的可恢复性。

本规格只调整库存缓存校准流程，不改变普通库存的 MySQL 事实源、`stock_sku.version` 单调版本协议、`stock_cache_repair` 状态模型、Redis Hash 字段或普通库存 API。业务库存扣减、确认和回滚仍先提交 MySQL 事实，再通过版本化 Lua 投影 Redis。

## 2. 已有证据与问题边界

本地完整商品目录包含 88,476 个 SKU。当前数据中 `stock_cache_repair` 均为 `APPLIED`，Redis 约有 88,486 个 `stock:available:{skuId}` Key。实测临时库存实例启动耗时约 18.71～19.25 秒，其中一次阶段计时为：建表 0.46 秒、旧协议扫描 0.65 秒、MySQL 全量读取 0.56 秒、无条件写入修复意图 2.17 秒、Redis 88K 条 Lua pipeline 6.53 秒，缓存阶段合计 10.38 秒；进程工作集峰值采样约 571 MiB，Redis 使用量约 11.2 MiB。后续暖启动实测中，当前“两次 pipeline（TYPE + HMGET）”在 88,476 条均匹配、差异 0、意图 0、写入 0 的情况下仍耗时 10.33 秒，校准总耗时 11.72 秒、应用启动 20.53 秒，产生约 188,957 条 Redis 命令，慢于旧的约 19.25 秒启动基线；该结果是本规格新增优化的直接依据。

现有实现的主要问题是：

1. 启动读取全部库存行到内存，数据量随 SKU 数线性增长。
2. 每次启动都执行全量 `stock_cache_repair` upsert，即使 Redis 与 MySQL 已经一致。
3. 每次启动都对全部 SKU 执行 Redis 投影，暖启动仍承担全量写负载。
4. 旧迁移与阻断重检使用 Redis `KEYS`，Key 数增长时会阻塞 Redis 主线程。
5. 仅依赖全局“已完成”标记无法发现单个 Redis Key 被删除、Hash 字段损坏或版本落后。

## 3. 冻结的数据与协议约束

### 3.1 事实源和版本

- MySQL `stock_sku.available_quantity` 与 `stock_sku.version` 是唯一库存事实。
- Redis `stock:available:{skuId}` 必须是 Hash，字段固定为 `quantity`、`version`。
- 版本化 Lua 只允许来源版本大于等于 Redis 当前版本时写入；Redis 版本高于来源版本时拒绝旧投影并将对应旧修复记录收敛为 `STALE`。
- 启动校准读取的 MySQL 行是某一时刻的快照。读取后发生的新库存事务会递增版本并写入新的 `stock_cache_repair`；旧校准批次即使发现差异，也不得覆盖更高版本。

### 3.2 修复意图

- 只有确认存在差异时，启动校准才创建或唤醒 `(sku_id, source_version)` 的 `PENDING` 修复意图。
- 已经 `APPLIED` 且来源版本未改变的修复记录不得被暖启动重新置为 `PENDING`。
- 同一 SKU 的更高版本修复意图仍由库存事实事务即时写入；启动校准不能删除、降级或覆盖它。
- Redis 读取失败、批次结果不完整或结果未知时，不能将对应 SKU 标记为 `APPLIED`；必须保留或创建可重试的修复意图。
- 全量兜底只表示“为每个当前 `stock_sku` 确保有可重试意图”，不代表同步执行全量 Redis 写入。

## 4. 启动校准流程

### 4.1 Redis 可用时的暖启动和冷启动

启动时按 `sku_id` 游标分页读取 MySQL，禁止一次性加载全表。每批建议 500～2,000 行，实际大小通过配置限定上界；查询使用 `WHERE sku_id > ? ORDER BY sku_id LIMIT ?`，不得使用深分页 offset。

对每个 MySQL 批次，使用一个有界、只读的 Redis 多 Key Lua 调用读取对应 Key 的 `TYPE`、`quantity` 和 `version`。建议每批 500～1,000 个 Key，脚本只执行 `TYPE`/`HGET`，不执行任何写命令，并按输入 Key 顺序返回固定三元组（类型、数量、版本）；调用失败、返回长度不正确或单项无法解析时，整批按 Redis 不可用/结果未知处理。该方式将约 18.9 万条读取命令收敛到约 89 次有界脚本调用，同时保留逐 SKU 的类型和版本判断。实现也可以在已证明更快且不改变语义的情况下采用 HMGET happy path + WRONGTYPE/异常 Key 的 TYPE fallback，但不能省略对缺 Key、缺字段和错误类型的识别。

批量只读脚本必须设置明确的 Key 数、返回字节数、执行时长和客户端超时上限；不得使用无界 Key 列表或全局扫描。Redis 脚本返回的是该批次内一致的只读观察结果，不得在脚本中写修复表或修改库存投影。比较结果分类如下：

| Redis 结果 | 启动动作 |
| --- | --- |
| Hash 且 quantity/version 与 MySQL 完全一致 | 不写修复表，不写 Redis |
| Key 不存在、Hash 缺字段、数量不同或 Redis 版本低于 MySQL | 以 MySQL 当前版本创建/唤醒 `PENDING` 意图；启动线程不直接投影，由带租约的修复器异步执行版本化 Lua |
| Redis 版本高于 MySQL | 不覆盖 Redis；对应 MySQL 快照意图标记 `STALE` 或不创建旧意图，等待更高版本事实记录收敛 |
| Key 类型不是 Hash | 不直接覆盖未知旧数据；记录 `REPAIR_BLOCKED`/迁移阻断事实并告警，按既有旧协议裁决流程处理 |
| Redis pipeline 连接失败、响应数量不完整或单项结果未知 | 本批不确认 `APPLIED`；按全量兜底规则确保修复意图可重试 |

批次内必须先持久化差异意图，再由现有 `repairPending` 按数据库租约认领并执行 Redis 投影，避免启动线程绕过多实例租约，也避免“Redis 已提交、进程在修复记录落盘前退出”。启动校准只提交当前批次差异 SKU 的意图，不直接调用 Lua；投影成功但进程在状态更新前退出时，修复器依据同一 `(sku_id, source_version)` 幂等重试。如果 MySQL 版本已提高，Lua 版本比较和条件状态更新共同保证旧批次不能覆盖新事实。

差异意图写入应使用一次 Mapper 批量操作（例如临时批次参数、批量绑定或等价的 `INSERT ... SELECT`），不得为每个 SKU 单独往返数据库。该操作必须保持 `stock_cache_repair` 的唯一版本键和状态单调性：已 `APPLIED` 的同版本记录只有在后续差异复核确认 Redis 当前缺失时才可条件唤醒为 `PENDING`。

Redis 完整丢失时，逐批比较会识别全部 Key 缺失并按批恢复；不得用全局 marker 直接跳过比较。冷启动与暖启动共用同一流程，区别只在实际差异数量。

### 4.2 Redis 不可用时的全量兜底

如果启动阶段 Redis 连接不可用，或任意批次连续读取失败达到配置阈值：

1. 停止继续执行 Redis 写入，避免在不确定连接状态下产生无界等待。
2. 通过单条 `INSERT ... SELECT` 或等价的数据库批量语句，为当前 `stock_sku` 确保修复意图；不得把 88K 行逐条写入。
3. 该语句必须保留已有更高版本记录和已完成状态的单调性；若同一来源版本已 `APPLIED`，不可无条件降为 `PENDING`。
4. 服务可以继续启动并提供依赖 MySQL 的业务能力；Redis 投影由带租约的定时修复器按批恢复。
5. `APPLIED` 只表示该来源版本的投影曾经成功，不能证明 Redis 当前仍保有对应 Hash。全量兜底语句必须保留同版本 `APPLIED`，但不得把它当作缺失 Key 的恢复凭据。
6. Redis 重新可用后，进程内必须启动一个有界、可重入的全量差异复核；若进程在不可用期间退出，下一次启动必须继续该复核。复核按 MySQL SKU 游标分页、Redis pipeline 读取数量/版本，发现 Key 缺失或内容不一致时，才将同版本 `APPLIED` 记录条件唤醒为 `PENDING`（或插入缺失意图），再交给带租约的投影器处理。启动复核本身不直接调用 Lua。
7. 差异复核可以使用持久化的 `last_sku_id`/扫描代次记录，也可以在单次进程内从游标 0 扫到末尾；无论采用哪种方式，都必须保证中断后能从安全位置重扫，不能只依赖全局完成 marker。复核与投影并发时仍以 Redis 版本 Lua 和数据库条件更新裁决。

全量兜底只在 Redis 读不可用或校准无法取得可信结果时使用。正常暖启动不能因为已有修复表记录就执行全量 upsert；Redis 恢复后的有界差异复核是另一条必要的读校准路径，不能省略。

### 4.3 旧协议迁移扫描

旧版 `stock:reservation:*:lines` 和阻断 Key 的扫描必须使用 Redis `SCAN` 游标，并设置每轮 count、最大处理时间和最大累计 Key 数。禁止生产路径调用 `KEYS`。扫描未完成时保持迁移保护状态，不能据“不完整扫描”判断没有旧预扣。

迁移阻断 SKU 仍按既有 `REPAIR_BLOCKED` 语义处理：先裁决旧预扣和 `stock_flow`，再删除旧字符串 Key、创建当前 MySQL 版本修复意图。新校准流程不得绕过阻断直接覆盖。

## 5. 资源和并发边界

- JVM 中同时保留的 MySQL 行、Redis 比较结果和投影结果不得超过一个配置批次；默认批次建议 1,000，硬上限建议 2,000。
- Redis 单次只读脚本的 Key 数、返回大小、执行时长和客户端超时必须有上限；默认批次建议 500～1,000，硬上限建议 2,000。连接超时、批次耗时和总启动校准超时均可配置。
- 启动校准不得持有长事务；每批 MySQL 读取使用短连接/短只读查询，修复意图写入使用独立短事务。
- 多实例通过 `stock_cache_repair.lease_owner/lease_until` 条件认领投影任务；Redis 锁不作为一致性依据。
- 允许多个实例同时进行只读差异扫描，但只有租约持有者可以推进修复状态；状态更新必须带 `(id, owner, status)` 条件。
- 定时修复任务仍限制每轮最大记录数、租约时长和退避时间；失败不能在启动线程中无限重试。
- 启动日志必须分开记录：分页读取耗时、Redis 批量读取耗时、差异数、意图新增/唤醒数、投影数、跳过数、阻断数、兜底是否启用、峰值批次内存；禁止只记录总耗时。
- 启动校准提交意图后允许异步收敛；日志和验收必须区分“差异意图已持久化”和“Redis 投影已完成”，不能把启动线程结束误报为缓存已恢复。

## 6. 正确性验收

以下验收必须在至少 88,476 SKU 的真实本地数据规模执行，并在 MySQL、Redis、修复表三方核对：

1. **暖启动无差异**：连续重启两次，差异数和投影写入数为 0；不产生新的修复意图，不把 `APPLIED` 降为 `PENDING`；启动耗时、JVM 峰值和 Redis 命令数显著低于当前 10.38 秒全量缓存阶段。
2. **局部丢失**：删除一个已存在的 `stock:available:{skuId}`，重启后仅该 SKU（及真实差异）产生修复意图和投影，数量与 MySQL 一致，版本等于 MySQL 当前版本。
3. **字段损坏/类型错误**：删除 `quantity` 或写入字符串类型 Key，必须进入修复或迁移阻断；不能静默标记成功，也不能覆盖旧协议未裁决数据。
4. **全量 Redis 丢失**：在独立的 Redis 测试数据库（例如 DB1）中清空普通库存投影，或使用全新空 Redis DB，不得对共享开发 Redis 数据库执行 `FLUSHDB`/`FLUSHALL`；重启后按有界批次恢复全部 SKU，最终每个 Hash 的数量/版本与 MySQL 一致，过程中 JVM 不持有全量行集合。
5. **Redis 不可用后恢复**：将 Redis 连接指向不可达端口，启动仍完成 MySQL 修复意图兜底；随后恢复到独立 Redis DB1，必须触发有界全量差异复核，即使数据库中对应版本的 repair 已为 `APPLIED`，缺失 Key 也必须被重新唤醒并最终收敛；不能只等待 `PENDING` 扫描，也不能要求再次人工重启。验收需分别记录复核完成、意图写入完成和异步投影完成时间。
6. **进程中断窗口**：分别在“差异意图提交后、Lua 前”和“Lua 成功后、状态更新前”终止进程，重启后同一版本最多产生一次有效投影，修复记录最终 `APPLIED` 或因更高版本变为 `STALE`。
7. **并发版本推进**：校准读取版本 N 后并发执行库存变更得到 N+1；校准不能把 Redis 回写为 N，最终 Redis 与 N+1 的 MySQL 事实一致。
8. **多实例竞争**：同时启动两个库存实例，最终无重复库存扣减、无错误 `APPLIED`、无永久租约；同一修复记录只有一个实例推进租约状态。
9. **旧协议保护**：扫描过程中存在旧预扣明细时，相关 SKU 不被全量覆盖；裁决后才按当前版本恢复，其他 SKU 不受阻塞影响。

## 7. 性能和资源验收

在同一台本地环境分别测量现实现状和修复后实现，固定 88,476 SKU、相同 MySQL/Redis 数据和相同 JVM 参数，至少记录三次取中位数：

- 暖启动：总耗时、MySQL 查询耗时、Redis 读取/写入命令数、修复意图 SQL 影响行数、投影条数。
- 冷启动：Redis 全量丢失时的总耗时、每批最大耗时和最终恢复时间。
- Redis 不可用：服务启动耗时、数据库兜底 SQL 耗时、恢复后最终收敛时间。
- JVM：峰值堆使用和工作集，确认不再随 SKU 数量复制全量行集合；至少采集 GC 次数和暂停时间。
- Redis：内存变化、瞬时命令速率、阻塞命令检查，确认不再使用 `KEYS`。
- Redis 差异扫描：记录脚本调用次数、每批 Key 数、脚本 P50/P95/P99 耗时、返回字节数和异常批次数；与当前两次 pipeline 基线的命令数和总读取耗时对比，确认 0 差异暖启动不因比较逻辑退化。
- MySQL：启动期间连接池占用、慢查询、锁等待和 `stock_cache_repair` 写入行数。

最低通过条件：暖启动不产生无条件全量 Redis 写入；无差异场景修复意图写入影响行为 0；局部丢失只修复局部差异；单批内存受配置上限约束；全量丢失和 Redis 不可用场景仍能在可重试状态下最终收敛。不得用单次本地快测推断生产容量。

## 8. 实现拆分与提交门槛

1. `backend` 先修改 `StockSqlMapper`：增加按 SKU 游标分页读取、批量差异修复意图写入/唤醒和保持状态单调性的 SQL；同步更新 `schema.sql` 或迁移脚本（如确有结构变化）。
2. `backend` 再修改 `StockCacheReconciler`：实现批次 Redis pipeline 比对、Redis 不可用全量兜底、`SCAN` 迁移扫描、批次计时和资源指标；不得改变库存 API 契约。
3. `backend` 补充单元测试和真实 Redis/MySQL 验收脚本，覆盖上述故障窗口、局部丢失和多实例租约。
4. 每一步先执行模块测试，再执行全仓 Maven 测试/打包和 `git diff --check`；测试失败不得宣告本批闭环。
5. 规格评审提交与实现提交分离；实现提交只包含库存后端、必要数据库迁移和测试，不混入 `bugfix_log.md`、本地性能产物或其他批次改动。

## 9. 明确不在本批范围

- 不改变秒杀 Redis 配额的最终确认/释放；该问题属于 CM-20260925-24。
- 不引入新的中间件、分布式缓存或全局一致性服务。
- 不以全局启动 marker 代替逐 SKU 差异检测。
- `StockConsistencyReconciler` 对 88K SKU 的周期审计长时间持有 Redis 锁、吞吐约 2K ops/s 的问题单独记录为 CM-20260924-26；本批只冻结启动差异校准和投影恢复，不扩展周期审计实现。
- 不宣称解决 2026-09-05 历史 MySQL 连接失败，除非另有故障注入证据。
