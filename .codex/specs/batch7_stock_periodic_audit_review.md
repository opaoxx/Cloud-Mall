# CM-20261002-26 库存周期对账资源评审规格

## 1. 评审结论与范围

本规格冻结普通库存周期对账的最小安全改造：将 `StockConsistencyReconciler.auditNormalStock` 从“每 30 秒全目录扫描并逐 Key 访问 Redis”改为“持久化 SKU 游标、有限批次、Redis 批量只读比较”。本批只处理普通库存周期审计的资源占用和调度异常边界，保留现有秒杀台账恢复、秒杀库存重建、旧预扣保护和版本化缓存投影语义。

本批不改变库存扣减、确认、回滚、秒杀受理或普通库存 API，不把周期审计升级为自动纠偏。审计发现差异时继续记录告警；真正的缓存写入只能由现有 `StockCacheReconciler` 的版本化修复流程完成。

## 2. 已确认现状和风险

- 本地目录约 88,476 个 SKU。`auditNormalStock` 先一次性加载 `findAvailableStock()` 的全量结果，然后对每个 SKU 分别执行 Redis `TYPE` 和 Hash `HGET`。
- 单轮曾观察到 Redis 约 1,700～2,200 ops/s，锁连续持有超过 40 秒；固定延迟任务随后继续进入下一轮，可能长期挤占 Redis、调度线程和连接池资源。
- 当前持有的是已有 `stock:consistency:lock`，20 秒租约由独立线程续期；失去租约后已有代码会停止后续写操作，但普通审计本身未分批保存进度。
- `stock_sku.version` 是普通库存事实版本；`StockCacheReconciler` 已有 `findAvailableStockBatchAfter(cursor, limit)` 和有界 Lua 批量读取三元组（类型、数量、版本）的能力。
- Redis 连接异常可能从定时入口直接冒泡为 Spring 调度器的 `Unexpected error occurred in scheduled task`；锁释放、续租或批量读取失败不能破坏后续秒杀恢复，也不能推进游标。

## 3. 冻结契约

### 3.1 事实读取和观察语义

1. MySQL `stock_sku(sku_id, available_quantity, version)` 是审计事实源。每个批次使用短查询读取，不得持有覆盖整个审计周期的事务。
2. Redis 批量读取必须返回与输入 SKU 顺序一一对应的 `type/quantity/version`。结果缺项、长度不符、字段无法解析、脚本超时或连接异常都视为本批“观察未知”。
3. Hash 且 `quantity` 与 `version` 同时匹配 MySQL 读取值时记录一致；缺 Key、错误类型、缺字段、数量不一致或 Redis 版本低于 MySQL 时只记录差异告警，不直接写 Redis。
4. Redis 版本高于 MySQL 读取版本时不得覆盖或把它判为可修复旧值，只记录“Redis 高版本”观察；并发库存更新由现有版本化 Lua 和持久修复任务裁决。
5. 批次读取发生库存更新时，审计结果只表示读取瞬间的观察，不得声称形成全局一致快照；下一周期按新的版本重新检查。

### 3.2 持久化游标

新增幂等的单行状态表 `stock_consistency_audit_state`，至少包含：

`state_key`（固定 `NORMAL_STOCK` 主键）、`cursor_sku_id`、`cycle_started_at`、`last_completed_at`、`last_batch_count`、`updated_at`、`last_error`。

约束如下：

- `cursor_sku_id` 表示已经完成并确认结果的最大 SKU；初始为 0。
- 每个批次成功完成 MySQL 读取和 Redis 批量观察后，才在同一短事务中推进游标；Redis 观察未知时不得推进该批次。
- 游标推进使用 `WHERE state_key=? AND cursor_sku_id=?` 条件，失败表示状态被其他实例推进，本轮停止；已有 Redis 租约仍是跨实例入口闸门。
- 游标超过当前最大 SKU 时，以短事务将其重置为 0 并写入 `last_completed_at`，开启下一扫描周期。重启从已持久化游标继续；批次中途进程终止时允许安全重复读取，不能跳过 SKU。
- 只允许按 `sku_id > cursor_sku_id ORDER BY sku_id LIMIT ?` 读取，禁止 offset 深分页和一次性全表加载。

本表只保存进度和最近失败信息，不保存库存副本，也不改变 `stock_cache_repair`、`stock_flow` 或秒杀台账状态。

### 3.3 批次、锁和资源上限

- 默认 `normal-audit-batch-size=500`，硬上限 1,000；Redis Lua 单次最多读取同一批次的 Key，返回大小和客户端超时必须有配置上限。
- 默认每次调度最多处理 4 个批次或 3 秒，以先达到者为准；达到上限后持久化当前游标并释放锁。不得为了追求一个完整周期而延长锁。
- 保留 `stock:consistency:lock` 作为跨实例互斥，锁 TTL/续租/compare-and-delete 语义不变。续租失败、token 不匹配或租约过期后，本轮立即停止普通审计并不得推进当前批次游标。
- 普通审计应在秒杀恢复前完成有限批次；无论普通审计是否因为 Redis 故障退出，都必须保证秒杀恢复的既有 guard、台账落库和缺失配额重建语义不被静默跳过。若本轮 Redis 不可用，应安全结束本轮并由下一次定时任务重试。
- 调度入口必须捕获 Redis 连接失败、批量脚本异常、锁释放异常和普通审计运行时异常，记录结构化告警并让 Spring 调度线程返回；不得让一次故障形成未处理的 `Unexpected error`。业务代码错误仍需保留日志和失败计数，不能伪装为成功。
- finally 释放锁只能使用当前 token 的 compare-and-delete；释放失败只记录告警，不能删除其他实例的新租约。

### 3.4 多实例、重启和数据变化

- 多实例先竞争 Redis 租约，只有持有者可读取并推进持久游标；未获取租约的实例直接返回。
- 进程在 MySQL 读取后、Redis 返回前崩溃时，游标保持旧值，下一轮安全重复；在批次结果持久化后崩溃时，下一轮从新游标继续。审计为只读观察，重复告警可按批次日志去重，但不得影响库存事实。
- 多实例不允许各自维护内存游标；数据库游标是重启恢复和审计覆盖周期的唯一进度来源，Redis 锁只负责短时互斥。
- 新增 SKU、删除 SKU 或 SKU 主键间存在空洞不影响 keyset 扫描。扫描结束时重置游标，下一周期覆盖新增 SKU；删除的 SKU 不产生 Redis 写入。

## 4. 覆盖周期和可观测性

默认 500 行、每轮最多 4 批、固定延迟 30 秒时，88,476 SKU 的理论覆盖上限约为 `ceil(88476/2000) * 30s ≈ 22.2 分钟`，实际以 MySQL/Redis 批次耗时为准。若部署环境达不到该上限，必须通过配置调高批次数或缩短调度间隔，但不得突破单批和单轮资源上限。

每次调度至少记录：是否取得锁、起止游标、处理批次数和行数、完成/未知/差异数量、MySQL 查询耗时、Redis 批量读取耗时、是否续租失败、是否因时间/批次上限提前结束、异常类型、周期完成时间。指标或日志必须能区分“未取得锁”“Redis 不可用”“结果未知”“发现不一致”和“周期完成”。

## 5. 故障验收门槛

实现前必须先补充针对冻结契约的测试，至少覆盖：

1. 88,476 行规模下，单次普通审计只保留一个配置批次，不再调用全量 `findAvailableStock()`；Redis 调用次数按批次而非按 SKU 的 `TYPE/HGET` 增长。
2. 第一个批次完成后模拟进程终止，重启从持久游标继续；批次中途异常时游标不推进，重试后不漏 SKU。
3. 两实例竞争时只有租约持有者推进游标；旧租约失效后不能释放新实例租约，也不能继续推进旧批次。
4. Redis 断连、脚本超时、返回长度错误和 `WRONGTYPE` 均被捕获并记录；调度入口不再向 Spring 冒泡未处理的 Redis 异常，游标保持安全位置，后续定时任务可恢复。
5. Redis 正常但 MySQL 版本在批次读取后递增时，审计只记录读取时观察，不写回 Redis、不创建或修改错误版本的修复记录。
6. 0 差异、局部缺 Key、Hash 缺字段、数量不一致、Redis 高版本分别得到正确分类；秒杀恢复和秒杀库存缺失重建在普通审计提前结束、失败和 Redis 暂不可用场景仍按既有测试通过。
7. 真实 88,476 SKU 规模连续运行至少一个完整周期，普通审计锁持有时间目标为单轮不超过 5 秒，Redis 命令速率和 JVM 堆不再随全量行集合增长；记录 P50/P95 批次耗时、最大锁时长和实际覆盖周期。若本机环境无法达到 5 秒，必须报告实测值和原因，不得宣称容量达标。

## 6. 实现边界与提交门槛

1. `backend` 先在 `StockSqlMapper` 增加审计状态表的幂等建表、状态读取、条件推进和游标批量读取；同步提供可重复迁移或启动建表方案。
2. `backend` 再改 `StockConsistencyReconciler`：批量只读 Lua、有限批次、持久游标、异常边界和观测日志；不得复用/改写秒杀业务状态机。
3. 仅补库存后端测试和必要数据库迁移；不修改 API、订单/支付/商品代码或 `bugfix_log.md`（由主 Agent 在实现批次开始前后维护）。
4. 规格评审与实现提交分离。实现前执行库存模块测试，完成后执行全仓 Maven `clean test package`、资源验收和 `git diff --check`；失败不得宣告闭环。

## 7. 明确不在本批范围

- 不自动修复普通库存 Redis 差异；修复仍由 `StockCacheReconciler` 的持久化意图和版本 Lua 完成。
- 不改变秒杀配额最终结算、接受台账、恢复队列或旧预扣迁移语义。
- 不引入新的分布式锁、中间件、消息队列或全局快照机制。
- 不以一次“扫描完成”标志替代逐 SKU 的版本观察，也不把本轮观察结果当作跨全周期事务快照。
